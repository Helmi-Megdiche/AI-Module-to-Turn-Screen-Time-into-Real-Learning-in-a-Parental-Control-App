## 1. Executive summary

- The existing Flutter module (`android-app`) already implements a robust MediaProjection chain for Android 13/14/15 (consent, foreground service, capture, recovery).
- The critical Android 14+ requirements are already satisfied in Flutter: `FOREGROUND_SERVICE_MEDIA_PROJECTION`, `foregroundServiceType="mediaProjection"`, and `startForeground(..., FOREGROUND_SERVICE_TYPE_MEDIA_PROJECTION)`.
- The screenshot plugin already includes the API 34+ guardrail: a single `MediaProjection` instance is scoped to a single valid VirtualDisplay session, with `resetSession()` for cleanup/re-consent.
- For `mobile-rn`, the best integration point is a new native package `com.mobilern.screenshot` and a TS wrapper `mobile-rn/src/services/screenshotService.ts`, surfaced through `TrackingScreen` (or a parent-only dedicated screen).
- Gates G1-G8 below are defined with observable criteria, logs, and pass/fail outcomes.

### 2.4 Native Android side: declared classes / services / permissions

- **Screenshot plugin classes**
  - `MediaProjectionScreenshotPlugin` (methods: `takeCapture`, `startCapture`, `stopCapture`, `resetSession`).
- **Consent / projection bridge classes**
  - `RequestMediaProjectionPermissionManager` (consent orchestration + callback).
  - `RequestMediaProjectionPermissionActivity` (launches `createScreenCaptureIntent()`).
  - `MediaProjectionService` (foreground service that receives projection consent data).
- **Flutter app permissions**
  - `INTERNET`, `PACKAGE_USAGE_STATS`, `FOREGROUND_SERVICE`, `FOREGROUND_SERVICE_MEDIA_PROJECTION`, `POST_NOTIFICATIONS`.
- **Service manifest declaration**
  - `<service ... android:foregroundServiceType="mediaProjection" />` in `media_projection_creator`.

### 2.5 Consent intent flow (MediaProjectionManager)

1. Dart calls `MediaProjectionCreator.createMediaProjection()`.
2. `RequestMediaProjectionPermissionManager.requestMediaProjectionPermission(...)` starts `RequestMediaProjectionPermissionActivity`.
3. The activity calls `MediaProjectionManager.createScreenCaptureIntent()` and then `startActivityForResult(...)`.
4. On result:
   - `RESULT_OK` -> explicit package-scoped broadcast `...request_permission_result_succeeded`.
   - otherwise -> `...failed_user_canceled`.
5. The manager receives the broadcast and creates projection:
   - Android Q+ -> starts `MediaProjectionService` in foreground.
   - < Q -> calls `getMediaProjection(...)` directly.
6. Callback returns result code to Flutter and stores the `MediaProjection` instance in the screenshot plugin.

### 2.6 Capture pipeline (VirtualDisplay / ImageReader / encoding)

- `ImageReader.newInstance(width, height, PixelFormat.RGBA_8888, 5)`.
- `mediaProjection.createVirtualDisplay(...)` using the ImageReader surface.
- `acquireLatestImage()` then bitmap conversion.
- **`takeCapture()`**: PNG compression (`Bitmap.CompressFormat.PNG`) and map return.
- **`startCapture()`**: continuous JPEG stream (`Bitmap.CompressFormat.JPEG`) via `EventChannel`.
- Payload includes `bytes`, `width`, `height`, `rowBytes`, `pixelStride`, `rowStride`, `nv21`, `time`, `queue`.

### 2.7 Android 14+ foreground service requirement (mandatory)

- Already implemented in Flutter chain:
  - manifest permission `FOREGROUND_SERVICE_MEDIA_PROJECTION`;
  - service `foregroundServiceType="mediaProjection"`;
  - `startForeground(..., ServiceInfo.FOREGROUND_SERVICE_TYPE_MEDIA_PROJECTION)` on API 29+.

### 2.8 Frame export format

- **Binary bytes** (plugin does not require file-path output).
- **Single shot**: PNG bytes.
- **Continuous mode**: JPEG bytes (stream).
- **NV21** provided additionally.
- Code comments show base64/file options, but they are currently inactive.

## 3. Flutter consumer behavior inventory (`android-app/lib`)

### 3.1 Where screenshots are triggered

- Capture is automatically triggered in a periodic loop (`Timer.periodic`) when monitoring is active and the foreground app is capturable.
- An immediate capture is also triggered at loop start (`_safeCapture()` initial call).
- Interval is risk-adaptive (`riskScore` -> 5s / 10s / 20s).

### 3.2 What is done with the result

- `takeCapture()` -> write temporary PNG -> compress to JPEG -> enqueue Workmanager upload (`registerOneOffTask`).
- Upload JSON payload to backend `/api/analyze` (`image` base64 + `userId` + `age`).
- Append local logs (`event_log.txt`) and update policy file (`capture_policy.json`).

### 3.3 Privacy / consent UX

- Explicit projection consent is requested before monitoring starts.
- Custom foreground notification text is configured (`"Screen capture active"`).
- Re-consent flow exists if projection becomes invalid (`resetSession()` + new permission request).
- No dedicated legal/privacy banner in UI; safeguards are mainly technical + flow-driven.

## 4. Cross-check Android 14 -> 15 (MediaProjection)

Verified references:
- [Android 14 - Foreground service types required](https://developer.android.com/about/versions/14/changes/fgs-types-required)
- [Android MediaProjection](https://developer.android.com/media/grow/media-projection)
- [Android 15 - Foreground service type changes](https://developer.android.com/about/versions/15/changes/foreground-service-types)

Key implications for Phase 2.3:

- FGS type `mediaProjection` must be declared in manifest for target API 34+.
- App must run a foreground service with a user-visible ongoing notification while projection is active.
- User consent is required per projection session.
- A single MediaProjection token/instance must not be reused for invalid repeated `createVirtualDisplay()` patterns (Android 14+ can throw `SecurityException`).
- User-side stop action ("Stop sharing") must trigger a clean state transition through `MediaProjection.Callback.onStop()`.

## 5. Proposed mobile-rn architecture

### 5.1 Native package

- New package: `mobile-rn/android/app/src/main/java/com/mobilern/screenshot/`
  - `ScreenshotProjectionManager.java` (session state, consent flow, projection callbacks).
  - `ScreenshotCaptureService.java` (mediaProjection foreground service lifecycle).
  - `ScreenshotModule.java` (React Native bridge module).
  - `ScreenshotPackage.java` (RN package registration).
  - `ScreenshotPrefs.java` (enable flag, TTL policy, last error, cache path metadata).

### 5.2 JS bridge API (locked contract)

- `requestProjectionConsent(): Promise<{granted: boolean; reason?: string}>`
- `startCapture(options): Promise<boolean>`
- `captureFrame(options): Promise<{bytesBase64?: string; filePath?: string; width: number; height: number; format: "png" | "jpeg"}>`
- `stopCapture(): Promise<boolean>`
- `getStatus(): Promise<{enabled: boolean; consentGranted: boolean; capturing: boolean; lastError?: string; lastCaptureAt?: number}>`

### 5.3 JS service wrapper

- New file: `mobile-rn/src/services/screenshotService.ts`
  - Android-only normalization.
  - Local TTL cache handling (automatic purge).
  - Optional upload policy (off by default).
  - Dedicated logs, e.g. `RN_SCREENSHOT`.

### 5.4 UI integration point

- Recommended entry point: extend `TrackingScreen` (or a dedicated parent-facing screen) with:
  - explicit toggle: "Enable screenshot capture";
  - "Grant consent" action;
  - "Capture frame now" action;
  - projection/service status badge;
  - explicit consent + notification explanation text.

### 5.5 Privacy-first defaults (locked)

- Capture is **disabled by default**.
- Explicit user consent required before any capture starts.
- Local-only cache storage with short TTL (e.g. configurable 15-60 minutes).
- Upload disabled unless explicitly enabled by parent settings.
- Mandatory cleanup on stop/revoke.

## 6. Gate definitions (G1-G8)

- **G1 Consent**: system consent dialog appears, user grants -> `getStatus().consentGranted == true`.
- **G2 Foreground service**: `startCapture()` -> persistent notification is visible + service-start logs are present.
- **G3 Frame validity**: `captureFrame()` returns a decodable image (`bytes > 0`, dimensions > 0).
- **G4 Revoke path**: user taps system "Stop sharing" -> callback stop -> state transitions to non-capturing without crash.
- **G5 Background behavior**: app backgrounded -> behavior follows design choice (continue or pause) and is explicitly documented.
- **G6 Process restart**: after process kill/restart -> consent must be requested again (no stale token reuse).
- **G7 Regression**: Phase 1 + Phase 2.1 + Phase 2.2 remain green.
- **G8 Performance sanity**: 10-minute capture run shows no obvious leaks, bounded battery impact, and no runaway loop.

Each gate must include: trigger action, expected logs, pass condition, fail condition.

Example log markers for runtime validation:

- G1: `RN_SCREENSHOT consent_requested`, `RN_SCREENSHOT consent_granted`
- G2: `RN_SCREENSHOT capture_started`
- G3: `RN_SCREENSHOT frame_captured bytes=<n>`
- G4: `RN_SCREENSHOT projection_stopped_by_system`
- G5: `RN_SCREENSHOT` with status `pausedInBackground=true` (design locked to pause in background)
- G8 failure guard: `RN_SCREENSHOT frame_retry attempt=<n>` and terminal `RN_SCREENSHOT frame_failed attempts=<n>`

## 9. Risks / open questions for review

- Android 15 strictness variance for "consent per session" across OEMs/devices (must be validated at runtime).
- RN output format choice: direct `base64` vs cache `filePath` (performance/memory trade-off).
- Storage policy: internal cache only vs external app-specific storage, and final TTL value.
- Encryption-at-rest requirement if frames contain sensitive PII.
- Notification copy + disclosure wording to align with Google Play policy expectations.
- Product decision for background behavior (continue capture vs intentional pause).
